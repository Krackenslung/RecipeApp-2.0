# Recipe app 2.0

Stack postgres 

## Recommended stack

**The constraint to design around:** a browser can't open a Postgres connection — Postgres speaks a raw TCP wire protocol, browsers only do HTTP/WebSocket. And credentials shipped in JS are public. So "frontend talks directly to the DB" has to mean *no hand-written Express layer*, not *no server*.

### Core

| Layer | Choice | Why |
| --- | --- | --- |
| Database | Postgres via **Supabase** | Auto-generated REST + realtime API over the schema (PostgREST) |
| Auth | **Supabase Auth** (GoTrue) | Native Google provider, issues the JWT that RLS reads |
| Authorization | **Row Level Security** | Replaces backend auth logic — enforced in the DB, not the client |
| Frontend | **React + Vite + TanStack Query** | Existing stack; `@supabase/supabase-js` for queries |
| Secrets / server work | **Vercel Functions** | Same deploy target as the frontend — one place for secrets |
| Hosting | **Vercel** | Vite build + `/api` routes picked up automatically |
| Image storage | **Supabase Storage** | Direct browser upload, storage RLS, CDN-backed public URLs |

### Row Level Security — the non-negotiable part

The browser uses a scoped `anon` key, not DB credentials. RLS is what makes that safe. Without it enabled, the anon key is effectively a public database.

Every table gets policies. Example for `recipes`:

```sql
alter table recipes enable row level security;

create policy "read own or public"
  on recipes for select
  using (user_id = auth.uid() or is_public = true);

create policy "write own"
  on recipes for insert
  with check (user_id = auth.uid());
```

### Google integration — splits in two

**User-scoped APIs** (Sign-In, Drive, Calendar) → browser-side OAuth with PKCE. No secret involved. Supabase Auth handles the Google provider and hands over the token.

**Anything with a server key** (Gemini, Places, Vision) → Vercel Function. Key lives in Vercel env vars; browser calls the function, function calls Google. Drop a file at `/api/generate.ts` in the repo root and Vercel picks it up — no config needed.

### Environment variables — the split that matters

```
VITE_SUPABASE_URL=...         # public by design
VITE_SUPABASE_ANON_KEY=...    # public by design, RLS protects it
GEMINI_API_KEY=...            # NO prefix — server only
SUPABASE_SERVICE_ROLE_KEY=... # NO prefix — bypasses ALL RLS
```

Anything with a `VITE_` prefix gets inlined into the client bundle at build time. The `service_role` key bypasses every RLS policy on the database, so if it ever lands behind a `VITE_` prefix the whole database is public. Worth a CI grep for `VITE_.*SERVICE_ROLE` to catch it.

### Image storage

Uploads go **straight from browser to Supabase** — no server hop. The client uploads with the user's own JWT and storage RLS enforces the rules.

`storage.objects` is just a table, so it takes policies like any other:

```sql
create policy "users upload to own folder"
on storage.objects for insert to authenticated
with check (
  bucket_id = 'recipe-images'
  and (storage.foldername(name))[1] = auth.uid()::text
);
```

This requires a path convention of `{user_id}/{recipe_id}/{filename}` — the policy reads the first folder segment and compares it to the caller's ID.

**Bucket type: public.** Recipe photos are meant to be seen, and public buckets give permanent CDN URLs that drop straight into `<img src>`. Private buckets need signed URLs that expire, meaning re-signing on every page load — real friction for something that isn't secret.

**Gotcha:** public bucket means anyone with the URL can view, and storage URLs are guessable if the paths are. Use `crypto.randomUUID()` for filenames rather than the original upload name.

Keep a separate *private* bucket only if something non-public shows up later (e.g. profile photos that shouldn't be enumerable).

### Alternative, not taken — self-hosted

Kept for reference. Closer to the existing toolchain, no vendor lock-in:

- **PostgREST in Docker** for the auto-generated API
- Same RLS policies (PostgREST reads the same JWT claims)
- A minimal **Express** service only for the secret-holding routes

More setup, full control.
